# 强制 Harness 任务协议设计

## 目标

让 Codex 与 Claude Code 对所有会形成项目交付、改动或调研结论的任务自动创建或恢复 Harness 上下文，并让没有真实 Harness 结果的改动不能通过交付检查。

## 非目标

- 不为纯聊天、一般知识问答或未指定项目的对话创建项目记录。
- 不记录原始提示词、命令参数、文件路径、源代码、密钥或工具输入。
- 不把现有 `.ai/tasks`、`.ai/reports` 的历史内容伪造为新的遥测数据，也不删除它们。
- 不启动常驻 Agent、自动重试、自动创建 worktree，或默认派发多个 Agent。

## 统一生命周期

每个受管任务都有一个稳定的 `taskId`，其状态及证据仍在 `.ai/harness/tasks/<taskId>.json` 和 `metrics.jsonl`。新增 `.ai/harness/events.jsonl` 作为只追加的结构化事件流；每条事件只包含时间、任务 ID、宿主、事件类别和预定义数值/分类字段。

`harness-session` 是唯一的自动入口：它在项目内创建或恢复 Harness、将任务转为 `in_progress`、写入 `task_started` 事件，并输出可供宿主保存的任务上下文。任务结束仍必须由执行者在实际运行验证后，用现有 `record-outcome` 写入事实。

## 双宿主执行边界

- **Claude Code：**插件的 `PreToolUse` 对写入型工具自动建立或恢复任务上下文，并记录策略判定；`PostToolUse` 写入已完成工具事件。若受管项目的 Harness 初始化失败，写入操作 fail closed。原有用户 Hook 不被修改。
- **Codex：**Codex 当前没有等价的用户级 `PreToolUse` 拦截点。受管全局策略要求 Agent 在第一次项目工具操作前自动运行 `harness-session`；真正的硬保证由同一套 `harness-enforce` 交付检查和项目 CI 提供，而非声称能够拦截桌面端的每一个工具调用。

因此，两端都无需用户手工创建任务；Claude 在工具边界强制，Codex 在交付边界强制。任何宿主都不能把缺少 Harness 记录的改动宣称为合格交付。

## 交付硬门

`harness-enforce --project <目录> --task-id <ID>` 只读检查：

1. 项目内 Harness 目录、安全任务记录和事件流都存在；
2. 任务已启动，且其最新结果为 `completed/passed`；
3. 结果含有实际验证命令和非负的实测验证耗时；
4. 事件流中至少有相同任务 ID 的 `task_started` 与 `verification_completed`。

失败时以非零退出码和不含私密输入的原因拒绝交付。项目通过 `project-constraints` 安装一个调用该命令的 CI/本地检查后，Codex 和 Claude 的交付都接受相同的机械约束。

## 自动指标

`harness-session` 保存任务起始时刻；`record-outcome` 增加完成事件。评估器从事件流计算任务总耗时与事件覆盖率，但绝不根据缺失字段推测澄清、返工或验证时长。澄清与返工仍由执行 Agent 在发生时显式记录，以避免从对话内容臆测。

## 兼容与迁移

首次启用不回填历史。旧 `.ai/tasks` 与 `.ai/reports` 保持原状；今后的任务才写入新的 Harness 事件流。现有项目只在用户授权启用其 Harness 交付检查后才修改项目 CI，避免框架安装扫描或改写无关仓库。

## 验收标准

- Node 测试证明会话自动建立、事件隐私约束、故障 fail-closed 和交付硬门的通过/拒绝路径。
- 运行时清单包含新脚本，安装后校验无漂移。
- Claude 插件 Hook 只替换插件自身 Hook 文件，未触碰用户现有 Hook 配置。
- Codex/Claude 受管策略和中文文档写明自动入口、宿主差异与可验证边界。
- 在 AlphaFoundry 对一个新任务执行实际预览、开始、验证结果和交付检查；若项目 CI 的写入未获单独确认，则只输出可复制的集成命令，不声称 CI 已启用。
