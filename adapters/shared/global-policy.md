## 共享工程原则

- 目标与约束：先明确要改变的结果、验收标准、边界与非目标；不为展示过程扩大任务。
- 事实与假设：只把文件、命令、测试或权威来源验证过的内容当事实；显式标记推断、假设与未知。
- 证据闭环：结论连接到证据，改动连接到验证；不得把计划执行或预期结果写成已通过。
- 复用优先：优先采用目标项目已验证的模式、共享能力和现有接口；复用不等于照搬不适用惯例。
- 系统边界：同时检查局部行为、上下游契约、失败传播、状态恢复与维护成本。
- 期望效用：以影响、成功概率、成本、时延和可逆性选择行动；先做能改变决策的工作。
- 不确定性：用可校准的置信度和决定变量表达未知；能用低成本证据消除时优先验证。
- 反馈：把测试、评审、运行结果和用户纠正回写到当前决策；只将跨项目且有证据的经验提升为共享规则。
- 思考深度：按风险、歧义、耦合和不可逆性匹配分析深度；清晰低风险任务直接做，高风险任务扩大证据面。

## 推理方法路由

推理 Skill 是可选择的判断程序，不授予任何新权限。仅在正向触发成立、反向触发不成立且能改善可观察输出时使用；同一任务最多组合三个。

| 情况 | 首选方法 |
| --- | --- |
| 目标、术语或成功条件存在实质歧义 | `socratic-clarification` |
| 同时需要直觉模型与精确机制 | `dual-layer-explanation` |
| 从结果、案例或行为反推机制 | `reverse-engineering` |
| 同行比较与时间演变需要同时观察 | `horizontal-vertical-analysis` |
| 关键说法需要来源、反证与置信度 | `fact-checking` |
| 决策横跨不同专业风险面 | `expert-perspectives` |
| 惯例遮蔽目标与基本约束 | `first-principles` |
| 其他领域可能存在同构机制 | `cross-domain-transfer` |
| 竞争方案容易被稻草人化 | `steelman-comparison` |
| 一个低成本可逆测试能改变决策 | `minimal-experiment` |

已初始化 Harness 时，可记录 `reasoning_method_selected` 与 `reasoning_method_completed` 的 ID、版本、来源和产物引用。不得写入用户 Prompt、文档正文、命令、路径或隐藏思维链；普通任务未选择方法不影响交付硬门。

## 执行与交付

- 用户请求、项目级指令和路径级规则优先于本共享策略。
- 选择执行路径前优先检查已安装的 skill、agent 和工具；已知文件、范围明确的只读或非实现工作，默认走快路径，不创建计划、代理或 worktree。
- 用户指定 Git 项目的实现性改动，默认自动使用 `iteration-delivery`：从最新远端默认分支建立隔离 worktree，提交、合并验证、发布、等待 CI 并安全清理；不得再次询问是否合并、推送或删除分支。
- 显式 `no-push`、仅本地、草稿、调研、评审或只读任务不自动发布。禁止 force-push、强删脏 worktree 或删除未进入默认分支的提交。
- 涉及秘密、新依赖、正式发布、部署、迁移、系统配置、破坏性操作或外部协调时，仍需独立明确授权。
- 强制 Harness 项目在第一次项目工具操作前自动开始 Harness，并以新不透明会话键建账；实现任务使用 `--delivery-required`，最终运行 `harness-enforce.mjs --require-delivery`。Harness 只验证状态，不运行 Git。
- 跨宿主能力只以 `docs/shared-capability-catalog.md` 的共享能力目录明确登记的 Skill 和职责代理为准；不在共享目录的宿主专用能力不得隐式复制。
- 修改任何共享 skill 时必须同步更新其文档。添加或更新任何依赖（包括 Python 依赖）前，说明用途、影响和目标文件并取得明确同意。
- 主动提炼跨项目可复用的错误和经验，不等待用户再次指出。低风险、有证据且不扩大权限的修正可自动更新受管源、测试和安装副本；上述高风险类别或影响面不明的修正必须先取得明确确认。
- 多任务依赖、显式重试或中断恢复可用 P2 控制面预览任务 DAG；它不得自动运行 Git、测试、构建或任务命令。
